# Receipt Intelligence operations

## State machine

`UPLOADED → QUEUED → PROCESSING → REVIEW_READY → CONFIRMED → REVERSED`

Upload or processing can move to `FAILED`; an authorized retry returns `FAILED → QUEUED`. Server-side policies reject every other transition. Failed, queued, and review-ready receipts never change inventory.

## Upload and storage

The client requests an upload target from `POST /api/receipts`, uploads directly with `PUT`, then calls `POST /api/receipts/:id/complete`. Object keys are generated by the server as `receipts/:storeId/:year/:month/:receiptId/:fileId.ext`; legacy keys remain readable. Filenames never determine object paths. Completion verifies ownership, presence, exact size, checksum, MIME signature, and image dimensions before queuing work. Database rows never contain image bytes, credentials, public URLs, or signed URLs. Reads use short-lived signed GET targets only after an authorized store-scoped receipt lookup.

Development may explicitly use the signed local adapter. Production requires the already-created private AWS S3 bucket, region, and least-privilege credentials documented in `.env.example`. Leave `RECEIPT_S3_ENDPOINT` blank for normal AWS resolution and keep `RECEIPT_S3_FORCE_PATH_STYLE=false`. Keep Block Public Access enabled, ACLs disabled, bucket-owner-enforced ownership enabled, SSE-S3 enabled, and lifecycle policy consistent with `ReceiptFile.retentionUntil`.

The application uses `PutObject`, `GetObject`, `HeadObject` (authorized by object read access), and approved cleanup through `DeleteObject`. It never creates/lists/deletes buckets or administers IAM. Application operation does not require object ACL permissions. `ListBucket` is not used by the adapter; if retained in the existing bucket policy, scope it to this bucket and the configured receipt prefix.

## Jobs and extraction

`pnpm receipts:worker` continuously claims database-backed receipt jobs; `pnpm receipts:worker:once` drains one batch. A hosted orchestrator may use the authenticated internal processing endpoint and webhook wake configuration. Delivery is retry-safe because only a queued `JobRun` can be claimed.

`RECEIPT_OCR_PROVIDER=mock` selects deterministic fixtures. Filenames containing `unreadable`, `provider-fail`, or `timeout` exercise review and recovery states. Production requires `RECEIPT_OCR_PROVIDER=azure`, the existing HTTPS endpoint/key, and API version `2024-11-30`. Generic `RECEIPT_OCR_*` names are canonical; the existing `AZURE_DOCUMENT_INTELLIGENCE_*` aliases are normalized centrally for compatibility. The worker retrieves private S3 bytes, submits them to `prebuilt-receipt`, polls to completion, and maps MerchantName, TransactionDate, Subtotal, TotalTax/Tax, Total, and Items (Description/Name, Quantity, Price, TotalPrice). Missing fields stay missing and confidence remains internal.

Azure authentication, endpoint, quota, rate-limit, timeout, availability, unsupported-image, cancellation, and malformed-response failures map to stable internal categories. Owner-facing copy remains plain. Rate-limit, availability, and timeout failures are durably re-queued with bounded backoff while attempts remain; permanent failures remain inspectable and manually retryable. No OCR path writes inventory.

## Browser-to-S3 CORS

Configure CORS on the existing bucket with the exact deployed origins. Replace the production placeholder; do not use `*` with credentials:

```json
[
  {
    "AllowedOrigins": ["http://localhost:3000", "https://tindahan.example.com"],
    "AllowedMethods": ["PUT", "GET", "HEAD"],
    "AllowedHeaders": ["content-type"],
    "ExposeHeaders": ["etag"],
    "MaxAgeSeconds": 300
  }
]
```

The bucket remains private; CORS only permits browsers to call an already-authorized signed URL.

## Deployment and smoke verification

Store all receipt variables as server-only deployment secrets; never prefix them with `NEXT_PUBLIC_`. Configure Preview and Production deliberately, add their exact origins to S3 CORS, and redeploy after changes. The required resources must already exist: one private AWS S3 bucket, bucket-scoped IAM credentials, and one Azure Document Intelligence resource with endpoint/key.

Normal tests never call AWS or Azure. `pnpm receipts:cloud-smoke` skips by default. To deliberately exercise the configured development resources with the non-sensitive generated fixture, set `RUN_RECEIPT_CLOUD_SMOKE=true` for that command. Set `RECEIPT_CLOUD_SMOKE_FILE` to test a specific permitted JPEG, PNG, or WebP file. Set `RECEIPT_CORS_ORIGIN` to the exact browser origin (for example, `http://localhost:3000`) to include an S3 PUT preflight assertion. The smoke test uploads a unique object, checks private/signed access, submits it to Azure, reports only safe status categories, and deletes the test object in `finally`. Billing and provider quotas may apply.

## AWS Lambda receipt worker deployment

The existing `tindahan-receipt-worker` function in `ap-southeast-1` can run the same receipt application service as the local `pnpm receipts:worker` loop. No AWS resources or S3 trigger are created by this repository change.

- Build and package: `pnpm lambda:receipt:build` (the `lambda:receipt:package` alias is equivalent).
- Compiled file: `dist/lambda/index.mjs`.
- ZIP artifact: `dist/lambda/tindahan-receipt-worker.zip`.
- Lambda handler setting: `index.handler`.
- Runtime/architecture: Node.js 22.x, `x86_64`.

The ZIP contains the bundled handler and runtime dependencies at its root. It contains no `.env`, source fixtures, development tests, or credentials. The build also loads the generated bundle and verifies that `index.handler` is exported.

The bundled `index.mjs` is larger than the Lambda console editor's 3 MB per-file viewing limit. After upload, the console may therefore report that it cannot open the file. This does not mean the ZIP upload or handler failed: the function executes the deployed file normally. Use the Lambda **Test**/**Invoke** controls and CloudWatch logs for the manual verification below; do not edit the generated bundle in the console.

### Lambda environment

Configure these as server-only Lambda environment values:

- `NODE_ENV=production`
- pooled Neon `DATABASE_URL`
- `RECEIPT_STORAGE_PROVIDER=aws`
- `RECEIPT_STORAGE_DIR=receipts`
- `RECEIPT_S3_REGION=ap-southeast-1`
- `RECEIPT_S3_BUCKET=<existing-private-bucket>`
- blank or omitted `RECEIPT_S3_ENDPOINT`
- `RECEIPT_S3_FORCE_PATH_STYLE=false`
- `RECEIPT_OCR_PROVIDER=azure`
- Azure endpoint/key and `RECEIPT_OCR_API_VERSION=2024-11-30`
- `RECEIPT_JOB_PROVIDER=database`

Do **not** add `RECEIPT_S3_ACCESS_KEY_ID` or `RECEIPT_S3_SECRET_ACCESS_KEY` to Lambda. The SDK detects Lambda and uses its execution role through the default credential chain. `NEXTAUTH_SECRET` is not required by this worker. Keep the database and Azure secrets in Lambda’s encrypted environment configuration and never use `NEXT_PUBLIC_` names.

The existing role needs CloudWatch logging and `s3:GetObject` on the configured `receipts/*` prefix. The Lambda handler does not create buckets, list unrelated objects, change ACLs, generate browser uploads, or delete receipt objects. It connects to Neon using the pooled URL and reuses one Prisma client across warm invocations; the handler does not disconnect after every event.

### Deployment and manual test

1. Run all verification commands, then `pnpm lambda:receipt:build`.
2. Confirm the ZIP contains root-level `index.mjs` and configure handler `index.handler`.
3. Upload the ZIP to the existing `tindahan-receipt-worker` function; do not create a replacement function.
4. Confirm the Node.js 22.x runtime, `x86_64`, environment values, role, and a timeout long enough for the bounded Azure operation (at least 120 seconds).
5. Upload a permitted receipt through the production application and complete the upload so its `ReceiptFile` is validated and durable job is queued.
6. Copy [the example S3 event](./aws-s3-object-created-event.example.json), replace its region, bucket, and encoded object key with that uploaded object, then invoke the Lambda test event manually.
7. Verify CloudWatch contains only safe identifiers/statuses, the job succeeds or records a stable failure, the receipt becomes ready for review, and inventory has not changed.
8. Repeat the same event and a two-record event; the duplicate must be ignored through the atomic job claim.
9. Only after manual verification, configure the S3 `ObjectCreated` notification on the existing bucket with the narrow `receipts/` prefix. This implementation intentionally does not add that trigger.

S3 can deliver the event before the browser confirmation has created the durable job. That condition is classified as retryable so S3 asynchronous delivery can retry the batch. A fresh `RUNNING` claim cannot be stolen; a claim left `RUNNING` for more than five minutes after a Lambda timeout can be reclaimed within its existing maximum-attempt limit. Missing database files, wrong buckets, wrong prefixes, malformed keys, cross-store key mismatches, completed jobs, and duplicate claims do not run OCR.

### Rollback and limitations

Keep the previous known-good ZIP or published Lambda version. To roll back, remove/disable any later-added S3 notification, restore the previous function code/version and environment configuration, and continue processing queued work with `pnpm receipts:worker` or the existing worker deployment. Receipt/job records remain durable in Neon; do not delete them during rollback.

S3 asynchronous delivery retries the whole event when a retryable record fails, so successful records can be delivered again; atomic claiming makes those replays harmless. Azure processing must fit the Lambda timeout. A VPC-attached Lambda needs outbound connectivity to Neon and Azure. Automatic trigger provisioning, Lambda concurrency tuning, dead-letter destinations, and infrastructure-as-code remain outside this deployment artifact.

## Matching and aliases

Candidates are resolved only inside the authenticated store: confirmed receipt alias, active barcode, exact normalized name, then bounded fuzzy name ranking. Numeric scores remain internal. A user-confirmed line learns a store-scoped alias during confirmation.

## Confirmation and reversal

Confirmation validates all included lines, duplicate acknowledgement, product availability, and the idempotency payload, then updates balances and appends immutable movements in one serializable transaction. Reversal is Owner-only, validates aggregate available quantity for each affected product, and appends compensating movements. Original history is never rewritten.

## API and authorization

All owner-facing routes resolve the user from the signed server session and the store from membership. No route accepts a client store ID. Owner and Staff may upload, review, and confirm; Product creation from review and reversal are Owner-only. The local signed-file route trusts only authenticated HMAC tokens with action and expiry, never an arbitrary object key.

## Fixtures

Any valid 320–12,000 pixel JPEG, PNG, or supported WebP can drive the deterministic mock. Use a normal filename for the prepared five-line fixture, `unreadable-receipt.png` for an uncertain line, `provider-fail.png` for a provider failure, and `timeout.png` for a timeout. Automated tests generate a valid PNG in memory and never call paid OCR.
